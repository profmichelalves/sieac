```
01. METODOLOGIA E PROCESSOS
==========================================================

ESCOPO E METODOLOGIA

Avaliação conduzida sob metodologia black-box, simulando um atacante externo sem conhecimento prévio da arquitetura interna do alvo. O engajamento seguiu o OWASP Web Security Testing Guide (WSTG) e cobriu cinco fases estruturadas:

1. Reconhecimento Passivo
Enumeração de DNS, análise de Certificate Transparency logs, coleta de OSINT, reverse DNS e perfilamento de ASN/ISP para mapear a superfície externa sem gerar logs no servidor.

2. Reconhecimento Ativo e Mapeamento de Superfície
Fingerprinting HTTP, detecção de stack tecnológico, análise de cabeçalhos de resposta, inspeção de bundles JavaScript (incluindo descompilação de assets minificados para extrair endpoints hardcoded, URLs internas e segredos), e enumeração de arquivos estáticos e caminhos de configuração acessíveis.

3. Identificação de Vulnerabilidades
Testes sistemáticos em fluxos de autenticação, controles de autorização, gestão de sessão, validação de entrada, políticas CORS, gates de controle de acesso, comportamento de parâmetros de API e tratamento de erros. Cada vetor de teste foi selecionado com base nos sinais identificados durante o mapeamento de superfície.

4. Exploração e Validação de Prova de Conceito
Todas as vulnerabilidades candidatas foram confirmadas com PoC reproduzível e mínimo. Nenhuma ação destrutiva foi realizada; operações de escrita foram limitadas a contas controladas pelo pesquisador. O impacto foi medido contra exposição real de dados, potencial de movimentação lateral e cenários de interrupção operacional.

5. Documentação e Guia de Remediação
Cada achado foi documentado com evidências exatas de request/response HTTP, score CVSS 3.1, classificação CWE e guia de remediação passo a passo validado contra o sistema em produção.

Nenhum dado de terceiros foi lido, modificado ou excluído em nenhum momento durante os testes.

02. RESUMO EXECUTIVO
==========================================================

Contexto

O SIEAC (Sistema de Acompanhamento Escolar) é uma aplicação web hospedada no GitHub Pages que utiliza Supabase como backend.

O sistema foi desenvolvido para auxiliar professores no gerenciamento de notas e frequências de alunos, importando dados do SIGEDUC (Sistema de Gestão Educacional do Rio Grande do Norte).

O teste foi realizado com acesso anônimo, utilizando apenas a chave pública (anon key) exposta no código JavaScript do frontend.

Achados Críticos

Foram identificadas vulnerabilidades críticas de controle de acesso.

O Row Level Security (RLS) do Supabase está completamente desabilitado em todas as 13 tabelas do banco de dados, permitindo que qualquer pessoa na internet acesse mais de 22.000 registros educacionais.

Mais grave ainda, a tabela de usuários expõe senhas em texto plano (não hasheadas) de 9 professores, incluindo contas governamentais com domínio @educar.rn.gov.br.

Adicionalmente, o banco aceita operações de INSERT sem autenticação, possibilitando envenenamento de dados.

Cadeia de Ataque

Um atacante pode:

1. descobrir a chave Supabase no código JavaScript público;

2. extrair todas as senhas em plaintext da tabela usuarios;

3. usar essas credenciais para acessar o SIGEDUC oficial do governo do RN ou outros serviços onde os professores reutilizam senhas;

4. inserir dados falsos de alunos ou notas no sistema SIEAC.

Esta cadeia permite tanto Account Takeover em sistemas governamentais quanto manipulação de registros acadêmicos.

Impacto no Negócio e Regulatório

A exposição de dados de 1.056 estudantes (menores de idade) constitui violação grave da LGPD (Lei 13.709/2018), especificamente dos artigos 14 (tratamento de dados de crianças e adolescentes) e 46 (medidas de segurança).

As multas podem chegar a R$ 50 milhões ou 2% do faturamento.

Além disso, a exposição de credenciais de servidores públicos estaduais pode configurar incidente de segurança que deve ser reportado à ANPD em até 72 horas.

O dano reputacional para a instituição de ensino e para o desenvolvedor é significativo.

Recomendação de Gestão

Ação imediata P0 (24 horas):

• Desabilitar o acesso público ao projeto Supabase ou habilitar RLS restritivo em todas as tabelas.

• Todos os 9 usuários afetados devem ser notificados para trocar suas senhas imediatamente, especialmente nos sistemas governamentais.

• O responsável pelo sistema (Prof. Michel Alves) deve ser contactado urgentemente.

Prazo para remediação completa: 7 dias.
```

```
O projeto Supabase utilizado pelo SIEAC está configurado com Row Level Security (RLS) completamente desabilitado em todas as 13 tabelas do banco de dados.
```

```
----------------------------------------------------------
O QUE É A VULNERABILIDADE
----------------------------------------------------------

Segundo o relatório, toda a autenticação do sistema foi implementada em JavaScript executado no navegador.

O processo descrito seria:

1.

Consultar o usuário no Supabase.

2.

Receber a senha em texto plano.

3.

Comparar localmente:

senha digitada == senha armazenada.

4.

Salvar o usuário completo no localStorage.

----------------------------------------------------------
POR QUE A FALHA EXISTE
----------------------------------------------------------

Segundo o relatório, foi adotada uma implementação simplificada ao invés da utilização do Supabase Auth.

O código compararia diretamente:

senha === user.senha_hash

no navegador.

----------------------------------------------------------
CONTEXTO SISTÊMICO
----------------------------------------------------------

O relatório aponta diversos problemas:

• a senha trafega em texto plano;

• a validação ocorre no cliente;

• a sessão é apenas um objeto salvo no localStorage;

• funções como isAdmin() e isGestao() confiam apenas nesses dados locais.

----------------------------------------------------------
COMO FOI ENCONTRADO
----------------------------------------------------------

A vulnerabilidade foi identificada através da análise estática do código JavaScript.

Segundo o relatório, o arquivo authService.js consulta diretamente a tabela usuarios e compara a senha no navegador.

Também foi identificado que o router utiliza verificações baseadas apenas no conteúdo do localStorage.
```

==========================================================
VALIDAÇÃO
==========================================================

Segundo o relatório, a validação ocorreu em duas etapas.

Etapa 1

Foi confirmado que a consulta ao Supabase retorna o campo:

senha_hash

contendo a senha em texto plano.

Esse comportamento já havia sido evidenciado no achado F-01.

----------------------------------------------------------

Etapa 2

Foi realizada inspeção do código JavaScript.

Segundo o relatório, a comparação ocorre literalmente:

senha_digitada === senha_hash

sem utilização de:

• hash;

• bcrypt;

• validação server-side.

Também foi observado que a função:

isAdmin()

apenas verifica:

localStorage.getItem("user").perfil_id == 1

Segundo o relatório, basta modificar esse objeto no navegador para obter acesso às telas administrativas.

==========================================================
CENÁRIO DE ATAQUE
==========================================================

Cenário A

Bypass utilizando DevTools.

O atacante abre:

F12

Console

e grava manualmente um objeto no localStorage simulando um administrador.

Ao recarregar a aplicação, o sistema passa a acreditar que aquele usuário possui privilégios administrativos.

----------------------------------------------------------

Cenário B

Interceptação de credenciais.

Segundo o relatório, como a senha trafega do servidor para o navegador em texto plano, ela pode aparecer em:

• logs;

• histórico;

• inspeção de rede;

• proxies.

----------------------------------------------------------

Cenário C

Combinação com F-01.

Como todas as senhas já estariam expostas pela vulnerabilidade anterior, o atacante sequer precisaria realizar bypass.

Poderia efetuar login legítimo utilizando as credenciais obtidas.

----------------------------------------------------------

Limitação

O próprio relatório ressalta que:

Enquanto o RLS permanecer desabilitado, o bypass de autenticação possui impacto reduzido, pois o atacante já possui acesso direto aos dados.

Entretanto, quando o RLS for corrigido, essa vulnerabilidade passará a ser o principal vetor de ataque.

==========================================================
PROVA DE CONCEITO
==========================================================

Segundo o relatório, o fluxo simplificado seria equivalente a:

async function login(email, senha) {

    buscar usuário;

    if (senha == senha_hash) {

        localStorage.setItem("user", usuario);

    }

}

E a função de autorização seria equivalente a:

function isAdmin() {

    return user.perfil_id == 1;

}

O relatório afirma que basta alterar o conteúdo salvo no localStorage para simular qualquer perfil de usuário.

==========================================================
IMPACTO
==========================================================

Impacto imediato

Qualquer pessoa poderia se apresentar como administrador modificando o localStorage.

----------------------------------------------------------

Escalada

As credenciais em texto plano permitem login verdadeiro como qualquer usuário.

----------------------------------------------------------

Impacto de confidencialidade

As senhas trafegam do servidor para o navegador.

----------------------------------------------------------

Impacto de integridade

Caso o RLS seja implementado sem corrigir a autenticação, qualquer usuário poderá contornar a proteção simulando privilégios administrativos.

==========================================================
IMPACTO NO NEGÓCIO
==========================================================

Segundo o relatório:

Toda a arquitetura de autenticação necessita ser reconstruída.

Não seria possível corrigir apenas pequenos trechos do código.

A autenticação client-side deve ser substituída por:

Supabase Auth

ou outro mecanismo server-side.

Também poderá ser necessária migração da estrutura da tabela usuarios.

----------------------------------------------------------

Impacto regulatório

Segundo o relatório:

O tráfego de senhas em texto plano viola princípios da LGPD.

Caso essas credenciais sejam utilizadas em outros serviços, poderá haver responsabilização por negligência.

Estimativa apresentada:

20 a 40 horas de desenvolvimento.

==========================================================
ANÁLISE DE EXPOSIÇÃO
==========================================================

Segundo o relatório:

Autenticação client-side é considerada um anti-pattern de segurança.

A validação de credenciais deve ocorrer exclusivamente no servidor.

Os controles recomendados incluem:

• Supabase Auth;

• JWT assinado;

• auth.uid();

• remoção completa da senha das respostas da API.

==========================================================
REMEDIAÇÃO
==========================================================

Causa raiz

Decisão arquitetural de implementar autenticação integralmente no frontend.

----------------------------------------------------------

Correção estrutural

Migrar para:

Supabase Auth

utilizando:

signInWithPassword()

Migrar os usuários existentes.

Atualizar todas as políticas RLS utilizando:

auth.uid()

Transformar a tabela usuarios em uma tabela de perfis vinculada ao auth.users.

Remover definitivamente a coluna:

senha_hash

----------------------------------------------------------

Verificação

Após a migração:

• login deve utilizar exclusivamente supabase.auth;

• consultas diretas à tabela usuarios não devem mais retornar senhas.

A ausência desses cabeçalhos não representa a vulnerabilidade mais grave do sistema.
